Context

The web app is the standard now. The ASTC Expo/React Native app was built before this web app, never launched, and is being shelved. We’re not converging two products — we’re salvaging useful patterns, schema, and code from the mobile codebase to accelerate the web app, which is our canonical product going forward.

A future mobile app will be a new app built to whatever standards the web app sets — not a port of ASTC, not something the web has to be compatible with.

This doc identifies what to lift, adapt, or skip from the ASTC codebase. No code is being changed here — it’s a salvage map.

TL;DR — lift / skip / defer

Worth lifting

  1. locationValidator schema shape — {address?, city?, state?, zip?, lat, lng, placeId?, name?}. Drop into bookings. Unlocks Maps, distance quoting, previews.
  2. notificationQueue + cron pattern — queue‑with‑retry for SMS (Twilio), email, push later. Web has nothing like it today.
  3. Quoting flow — distance × per‑mile + surcharges. Wire to Google Routes API, not mobile’s Haversine shortcut. Feeds web’s existing rich rateProfiles math.
  4. tripShares table — public token‑based shareable links.
  5. auditLogs table — system‑wide mutation audit beyond bookingEvents.
  6. idempotencyKeys table — prevents duplicate booking submissions on retries.
  7. Twilio approach — not mobile’s code (deleted). Build fresh as a Convex action; the schema already models "sms" as a handoff channel.

Skip

  • Clerk auth (@clerk/clerk-expo, webhook sync, etc.).
  • Expo push tokens / pushTokens table.
  • react-native-maps, @appandflow/react-native-google-autocomplete, @mapbox/polyline.
  • (driver) and (owner) Expo UI stacks — RN-specific.
  • syncQueue / syncLogs (LimoAnywhere) — unless it’s on the roadmap.

Defer (useful, not urgent)

  • recurringBookings + cron generator.
  • bookingStops multi-stop trips.
  • tripReceipts (PDF in Convex _storage).
  • featureFlags table (mobile already modeled a web scope).

Recommended sequencing

This is a doc, not a sprint plan, but a sensible order if you start lifting:

  1. Google Maps + structured locations — biggest customer‑visible win.
    • Add locationValidator; migrate bookings.pickupLocation/dropoffLocation via widen‑migrate‑narrow per the convex‑migration‑helper skill.
    • Add @vis.gl/react‑google‑maps to BookingCard.tsx.
    • Add convex/actions/routes.ts calling Google Routes API; populate estimatedDistance / estimatedDuration at quote time.
    • Wire into rateProfiles quoting math.
  2. notificationQueue + Twilio SMS for dispatch handoffs.
    • Add notificationQueue table.
    • Add convex/actions/twilio.ts (sendSms).
    • Add convex/crons.ts with processNotificationQueue.
    • Hook into handoffs.create when channel === "sms".
  3. idempotencyKeys + auditLogs — small, safe drop‑ins.
  4. tripShares — small, customer‑facing win.
  5. Everything else (recurring, multi‑stop, receipts, customer accounts) when actually needed.

Verification

Research artifact — nothing to run. To pressure‑test:

  1. Confirm web has nothing to throw away: rg ‑i 'twilio|TWILIO_' src convex from web root returns only schema "sms" mentions (no SDK, no send code). rg ‑i 'google.*map|@vis.gl|@react‑google‑maps|placeId' src convex returns nothing.
  2. Confirm mobile schema additions are drop‑in: open mobile convex/schema.ts and verify locationValidator, notificationQueue, tripShares, auditLogs, idempotencyKeys have no Clerk‑specific (clerkId) or Expo‑specific (pushTokens) coupling.
  3. Confirm web’s rateProfiles is richer than mobile’s pricingConfig: open web convex/schema.ts at rateProfiles — it has base/mile/hour/airport/peak/tax math; mobile’s pricingConfig is just a mode toggle.
  4. Confirm Better Auth + Twilio is a real path: Better Auth supports custom auth providers and OTP delivery hooks. Follow‑up spike when customer phone‑OTP becomes a requirement.

Out of scope

  • Actual implementation. This is a salvage map; each lift in “Recommended sequencing” is its own implementation plan.
  • Mobile‑app revival. ASTC is being shelved. A future mobile app is a new project against web’s standards.
  • LimoAnywhere sync. Only lift if it’s confirmed on the roadmap.
  • Customer‑account UX decisions on web. Out of scope until product confirms accounts are coming.
